# Раздельные контракты AI-провайдеров

## Статус

Accepted

## Контекст

Первый `AIProvider` объединял чат, распознавание и синтез речи в одном объекте.
Это было удобно для раннего MVP, но связывало три независимо заменяемые
возможности. `ConversationService` получал методы речи, а `VoiceService` не мог
явно использовать разные STT и TTS adapter. Общие endpoint и ключ также мешали
безопасно переключать только одну часть голосового конвейера.

## Решение

Ввести три узких application port:

- `ChatProvider`;
- `SpeechRecognitionProvider`;
- `SpeechSynthesisProvider`.

Для OpenAI-compatible API использовать отдельные adapter и отдельные dependency
factory. `ConversationService`, `VoiceService`, калибровка и тестовая студия
получают только необходимые им контракты.

STT и TTS могут иметь собственные Base URL и API-ключ. Если отдельное значение
не задано, сохраняется совместимая цепочка fallback: общий Speech endpoint/key,
затем LLM endpoint/key. После завершения переходного периода старые
`AIProvider` и `OpenAIProvider` удалены: ни production wiring, ни тесты, ни
внутренние интеграции их больше не используют.

Публичные REST API, модели запросов и ответов не меняются.

## Альтернативы

- Оставить общий provider и добавить в него больше настроек: отклонено, потому
  что зависимость сервисов от лишних возможностей и искусственная связанность
  сохраняются.
- Создать единый универсальный plugin SDK сейчас: отклонено как преждевременная
  абстракция до появления второго adapter хотя бы для одного контракта.
- Удалить старый facade немедленно: на первом этапе отклонено ради
  инкрементальной миграции. Удаление выполнено после проверки всех внутренних
  вызовов и завершения совместимого периода.

## Последствия

Положительные:

- LLM, STT и TTS заменяются и тестируются независимо;
- сервисы следуют принципу разделения интерфейсов;
- существующая production-конфигурация продолжает работать без изменений;
- новые adapter не требуют изменения бизнес-логики Gateway.

Отрицательные:

- число provider factory и полей конфигурации увеличилось;
- старые внутренние вызовы composite provider больше не поддерживаются; каждый
  новый adapter должен реализовывать один или несколько узких контрактов явно.
