# Clean-room disaster recovery для трёх хостов

## Статус

Accepted

## Контекст

Family AI работает на трёх независимых VM/LXC: Gateway, PostgreSQL и Speech.
Воспроизводимый release-controller восстанавливал код на уже подготовленном
хосте, но не создавал PostgreSQL, не переносил runtime-секреты и не умел
поднимать систему на трёх полностью чистых VM.

Нужны два сценария:

1. все VM и база потеряны;
2. прикладные VM потеряны, но старая PostgreSQL ещё доступна по SSH и может
   отдать логический snapshot.

Исходные голосовые записи не хранятся и поэтому не являются объектом
восстановления. В Git отсутствуют API-ключи, пароли и runtime-конфигурация.

## Решение

Добавить DR-слой поверх существующего commit-based release-controller:

- зашифрованный DPAPI DR-kit содержит Gateway, Speech и Speech runtime
  конфигурацию;
- три целевых хоста загружаются идемпотентными root-скриптами для Debian 13;
- целевые хосты обязаны быть пустыми; существующая `family_ai` никогда не
  перезаписывается;
- при полной потере PostgreSQL создаётся новая роль и пустая БД, после чего
  Alembic применяет все миграции;
- при salvage источник сначала создаёт consistent custom-format `pg_dump`;
- до и после dump сравниваются точные количества строк и версия Alembic, чтобы
  обнаружить продолжающуюся запись;
- dump передаётся только через SSH/SCP, проверяется SHA-256 и восстанавливается
  в пустую целевую БД одной транзакцией;
- перед миграциями exact manifest восстановленной БД сравнивается с manifest
  источника;
- Gateway и Speech подготавливаются из одного точного Git commit, Speech
  активируется первым, Gateway — последним;
- после health-check включаются узкие nftables-ограничения для PostgreSQL,
  Speech и node_exporter;
- временные dump, пароли и расшифрованные env удаляются в `finally`;
- итоговый отчёт не содержит секретов или содержимого сообщений.

DR-kit защищён Windows DPAPI CurrentUser. Он не хранится в Git и не переносим на
другой компьютер или в другую учётную запись без отдельного защищённого
экспорта. Это сознательная граница текущих сценариев: VM потеряны, но
администраторский Windows-компьютер и репозиторий доступны.

## Альтернативы

- Восстанавливать VM из гипервизорных backup: отклонено как единственный
  механизм, потому что пользователь не использует backup и хочет независимый
  clean-room путь.
- Копировать каталог PostgreSQL: отклонено из-за зависимости от версии,
  настроек кластера и риска неконсистентного физического снимка.
- Хранить пароли и `.env` в Git: отклонено из-за раскрытия семейных и внешних
  секретов.
- Автоматически перезаписывать существующую целевую БД: отклонено как
  недопустимо разрушительное поведение.
- Сразу вводить pgBackRest/WAL archive: отложено. Это улучшило бы RPO, но
  означает постоянную backup-инфраструктуру, которой сейчас нет.

## Последствия

Положительные:

- восстановление не зависит от старых дисков Gateway и Speech;
- salvage сохраняет историю, агентов, safety-конфигурацию и родительскую память;
- один orchestrator проверяет адреса, SSH, место, dump и health всех служб;
- секреты не выводятся и не попадают в Git.

Отрицательные:

- в сценарии полной потери история и долгосрочная память безвозвратно теряются;
- DR-kit нужно обновлять после изменения runtime-секретов;
- первый запуск Speech может быть долгим из-за загрузки моделей;
- DPAPI-kit не защищает от одновременной потери VM и Windows-компьютера;
- реальная готовность подтверждается только отдельным fire drill на тестовых VM.
