# Подписанные воспроизводимые Android-релизы

## Статус

Accepted

## Контекст

Flutter-клиент собирался как debug APK и release build также использовал
стандартный debug-ключ. Такой APK нельзя считать управляемым релизом: ключ не
является проектной идентичностью, а сборка не связывается с точным Git commit.

Android разрешает обновить установленное приложение без удаления данных только
при одинаковых `applicationId` и ключе подписи. Потеря release-ключа означает,
что последующие версии нельзя установить поверх существующей.

Signing secrets не должны попадать в Git, build archive, stdout или общий
каталог артефактов.

## Решение

- Сохранить стабильный `applicationId` `ru.familyai.mentor`.
- Создать один проектный RSA-ключ в PKCS12 keystore вне репозитория, в профиле
  текущего Windows-пользователя.
- Хранить путь и пароли во внешнем `key.properties`. Gradle читает только этот
  файл и прекращает release-сборку, если signing configuration отсутствует.
- Создать DPAPI CurrentUser recovery-kit в игнорируемом каталоге `.dr`.
- Не передавать пароли через Gradle CLI и не печатать их.
- Собирать APK из `git archive` точного commit в одноразовом каталоге внутри
  `.artifacts`.
- После сборки проверять APK через `apksigner`, читать package/version через
  Android build tools и выпускать SHA-256 с JSON manifest.
- Удалять распакованные исходники после завершения или ошибки сборки.

Воспроизводимость означает одинаковые отслеживаемые исходники и проверяемую
привязку артефакта к commit. Она не обещает побайтово одинаковый APK: Gradle и
Android tooling могут включать изменяемые timestamps или служебные метаданные.

Первый переход с уже установленного debug APK требует удаления debug-версии:
Android намеренно запрещает обновление приложением с другим сертификатом. Адрес
Gateway при этом вводится повторно один раз. Все последующие release APK с тем
же ключом устанавливаются поверх предыдущего через `adb install -r`, сохраняя
SharedPreferences с адресом Gateway.

## Альтернативы

- Продолжить использовать debug key: отклонено, потому что это не проектная
  release-идентичность и ключ может быть незаметно пересоздан.
- Хранить keystore и пароли в Git: отклонено из-за раскрытия signing identity.
- Передавать пароли параметрами командной строки: отклонено из-за истории shell
  и списка процессов.
- Сразу вводить Google Play или MDM: отложено; приложение используется только в
  домашней сети и устанавливается родителем.
- Гарантировать бесшовный debug-to-release upgrade: невозможно из-за проверки
  подписи Android без сохранения небезопасного debug-ключа как постоянного.

## Последствия

Положительные:

- каждая production-сборка подписана постоянным проектным ключом;
- источник APK однозначно связан с Git commit;
- секреты не входят в source archive и артефакты;
- release-to-release обновления сохраняют локальный адрес Gateway и кеш.

Отрицательные:

- первоначальный переход с debug требует переустановки и повторного адреса;
- DPAPI-kit восстанавливается только той же Windows-учётной записью на том же
  компьютере;
- потеря и keystore, и recovery-kit исключает обновление уже установленного
  приложения;
- сборка зависит от локально подготовленных Flutter, JDK и Android SDK.
