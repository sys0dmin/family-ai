# Одноразовый мультимодальный ход «Покажи и спроси»

## Статус

Accepted

## Контекст

Android-клиент умеет отдельно отправлять голосовой ход и отдельно выбирать
готовую фотографию с текстовым вопросом. Лера пока не читает, поэтому основной
сценарий должен позволять выбрать или сделать снимок, задать вопрос голосом и
услышать ответ.

Chat, STT, TTS и Vision уже имеют независимые provider-интерфейсы. Нельзя
объединять их в один vendor-specific multimodal provider или передавать бинарные
данные в обычный LLM-контекст.

## Решение

Добавить `POST /v1/multimodal/{conversation_id}/turn`, который принимает ровно
два multipart-файла:

- `image`: один JPEG, PNG или WebP;
- `audio`: один поддерживаемый голосовой формат;
- необязательную длительность записи.

Новый application service:

1. проверяет capability `image_understanding` у агента;
2. параллельно запускает STT и получение ограниченных Vision-наблюдений;
3. удаляет бинарные ссылки после завершения HTTP-запроса;
4. передаёт в `ConversationService` только транскрипцию и недоверенный
   текстовый runtime context;
5. использует отдельный safety context из Vision-наблюдений для правил еды,
   лекарств, электричества, огня и острых предметов;
6. запускает TTS только для уже прошедшего output-safety ответа;
7. возвращает аудио и идентификатор сохранённого сообщения тем же контрактом,
   что обычный voice turn.

`ImageUnderstandingService` остаётся владельцем проверки типа, сигнатуры,
размера и agent capability. Он предоставляет операцию получения эфемерных
наблюдений, которую используют как старый текстовый Vision endpoint, так и
новый мультимодальный service.

Voice metrics получают тип хода и отдельную длительность Vision. Они не содержат
вопрос, описание изображения, имя файла или conversation id.

Android расширяет существующий voice-controller. Pending photo существует
только в памяти до ответа, ошибки или отмены. Камера и галерея скрыты за
маленьким client-side port, чтобы сценарий тестировался без Android plugin.
Поздний HTTP-ответ после отмены игнорируется. Физическая отмена уже принятой
сервером работы не гарантируется текущим one-shot HTTP transport.

## Safety

- Vision-наблюдения считаются недоверенными и могут быть ошибочными.
- Фото не используется для идентификации человека, точного адреса, здоровья или
  иных чувствительных признаков.
- По изображению нельзя подтверждать съедобность, лекарство, электрическую или
  механическую безопасность.
- Агент может объяснить видимое и предупредить, но опасную часть выполняет
  родитель.
- Личные фотографии и записи Леры не входят в Git regression suite.

## Альтернативы

- Передавать изображение и аудио прямо в ChatProvider: отклонено из-за жёсткой
  связи с одним мультимодальным поставщиком.
- Сначала выполнять STT, затем Vision с транскрипцией: отклонено как базовый
  путь из-за лишней последовательной задержки. Vision получает нейтральный
  запрос на наблюдения, а вопрос учитывает итоговый агент.
- Сохранять фото для replay: отклонено; повторяется только готовый TTS-ответ.
- Создать отдельный сетевой Vision Service сейчас: отложено, provider port уже
  сохраняет возможность вынесения.
- Ввести WebSocket на этом этапе: отложено до Voice 2.0; one-shot multipart API
  проще и сохраняет обратную совместимость.

## Последствия

Положительные:

- ребёнку не нужен текстовый ввод;
- провайдеры заменяются независимо;
- STT и Vision выполняются параллельно;
- существующие voice replay, safety и история переиспользуются;
- бинарные данные не становятся частью product data.

Отрицательные:

- клиент не видит точную серверную границу STT/Vision/LLM до появления
  потокового транспорта;
- параллельный запрос увеличивает одновременную нагрузку на локальный Speech и
  внешний Vision;
- отмена на клиенте не гарантирует прекращение уже начатого server inference;
- качество ответа всё ещё зависит от точности двух независимых моделей.
