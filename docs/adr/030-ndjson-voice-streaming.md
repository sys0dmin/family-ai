# Потоковый Voice 2.0 через NDJSON

## Статус

Accepted

## Контекст

Текущий voice turn возвращает один WAV только после завершения STT, LLM и
синтеза всего ответа. На J3710 длинный ответ дал следующий baseline:

- STT: 9,1 с;
- Vision: 3,2 с параллельно с STT;
- LLM: 2,0 с;
- TTS: 18,3 с;
- полное серверное время: 29,5 с.

Главная задержка находится в TTS. Локальный Silero не предоставляет потоковые
семплы, но provider-neutral Gateway может разделить уже безопасный текст по
границам предложений и последовательно вызвать существующий
`SpeechSynthesisProvider`.

Нельзя начинать озвучивание токенов LLM до завершения output-safety: поздняя
опасная часть ответа иначе может быть обнаружена после того, как начало уже
проиграно ребёнку.

## Решение

Добавить обратно совместимые streaming endpoints для обычного голосового и
мультимодального хода. Старые endpoints с единым аудиофайлом остаются fallback.

Поток имеет `Content-Type: application/x-ndjson`. Каждая строка — отдельное
событие протокола `family-ai-voice/2`:

- `started` — содержит случайный `turn_id` и позволяет немедленно отменить ход;
- `message` — сообщает сохранённый `message_id` после полного input/output
  safety и количество ожидаемых частей;
- `audio` — содержит индекс, MIME-тип и base64 одного законченного аудиофайла;
- `complete` — подтверждает успешное завершение;
- `error` — возвращает стабильный код и безопасный детский текст после того,
  как HTTP-заголовки уже отправлены.

NDJSON выбран вместо SSE, потому что запрос является multipart POST, а не
долгоживущим GET. WebSocket не нужен для однонаправленного ответа и усложнил бы
повторную отправку файлов, reverse proxy и fallback. Бинарный собственный
framing уменьшил бы размер, но потребовал бы более сложного и менее
диагностируемого парсера. Base64 добавляет около 33% сетевого объёма; в домашней
LAN это приемлемо, а CPU TTS остаётся доминирующей стоимостью.

Разбиение текста принадлежит application layer, а не TTS provider. Provider
по-прежнему реализует только стабильный контракт `text → audio` и может быть
заменён без изменения Conversation Service.

Android начинает последовательное воспроизведение при получении первой части.
Полученные WAV-части объединяются локально в один корректный WAV и записываются
в существующий 10-дневный replay-кеш. Если потоковый endpoint недоступен,
клиент автоматически использует старый one-shot endpoint.

## Safety и жизненный цикл

Порядок неизменяем:

1. STT и, при необходимости, Vision;
2. Conversation Service;
3. полный output-safety;
4. разбиение уже проверенного ответа;
5. TTS и воспроизведение частей.

Фотография и запись не попадают в события, историю или метрики. В событиях нет
транскрипции и текста ответа. Base64 содержит только готовый ответ TTS.

## Отмена

Gateway регистрирует активную asyncio task по случайному `turn_id`.
`DELETE /v1/voice/streams/{turn_id}` отменяет provider await, прекращает
дальнейший синтез и закрывает поток. Android одновременно останавливает
проигрыватель и инвалидирует локальную операцию, поэтому части разных ходов не
смешиваются.

CPU-вызов Silero выполняется в рабочем потоке Python и не может быть безопасно
прерван посередине одного предложения. Отмена гарантированно предотвращает
следующие части и выдачу результата, но уже начатый короткий Silero chunk может
доработать в фоне. Размер chunk ограничивает эту задержку.

## Метрики

Gateway измеряет:

- время STT, Vision, LLM и полного TTS;
- время до готовности первой аудиочасти;
- количество частей;
- полное время;
- streamed/fallback mode;
- число отмен.

Android один раз сообщает время от завершения записи до фактического перехода
проигрывателя в состояние `playing`. В метриках нет conversation id, текста,
аудио или имени файла.

## Альтернативы

- Потоковые токены LLM сразу в TTS: отклонено из-за невозможности полного
  output-safety до первого звука.
- SSE: отклонено для multipart POST и бинарных частей.
- WebSocket: отложено; двунаправленный постоянный канал не нужен текущему
  сценарию.
- Менять provider interface на streaming TTS: отклонено как обязательное
  требование. Будущий provider может оптимизировать синтез внутри адаптера, не
  меняя application protocol.
- Только сокращать ответы: полезно и применяется как modality guidance, но не
  решает длинные сказки, инструкции и явно запрошенные подробные ответы.

## Последствия

Положительные:

- первый безопасный фрагмент звучит до завершения полного TTS;
- старые клиенты и providers продолжают работать;
- отмена получает серверный идентификатор и прекращает оставшуюся работу;
- replay сохраняется без повторного синтеза;
- реальная воспринимаемая задержка становится измеримой.

Отрицательные:

- новый клиентский parser и состояние playlist увеличивают сложность;
- base64 увеличивает LAN-трафик;
- несколько коротких TTS-вызовов могут немного увеличить полное CPU-время;
- текущий Silero chunk нельзя прервать внутри native/worker-thread вызова.
