# Локальный release gate и серверный барьер схемы

## Статус

Accepted

## Контекст

Проект уже имеет отдельные unit, integration, visual, documentation и release
archive проверки, но их нужно помнить и запускать разными командами. Пропуск
одной проверки создаёт релиз, который формально здоров по HTTP, но может не
соответствовать документации, мобильным baseline или database schema.

22 августа 2026 года Gateway-код с новой Alembic revision был активирован до
явной фазы миграции. Health-check и smoke-test не обнаружили проблему, потому
что затронутый SQL CHECK выполнялся только при последующем пользовательском
действии. Это подтвердило, что локальный quality gate и runtime schema guard
решают разные задачи и нужны одновременно.

Использовать внешний CI для домашнего контура не требуется: он добавит внешнюю
зависимость и риск отправки метаданных без пользы для единственного локального
production.

## Решение

Добавить один PowerShell runner `Invoke-LocalReleaseGate.ps1`, который работает
только над чистым текущим Git commit и композиционно вызывает существующие
проверки. Runner не дублирует их бизнес-логику. Он создаёт локальный
machine-readable отчёт в `.artifacts`, но не выполняет deploy.

До тестов runner также выполняет `uv lock --check` отдельно для Gateway и Speech.
Lock-файлы являются частью воспроизводимого релиза, поэтому рассинхронизация
manifest и lock блокирует выпуск так же, как упавший тест.

Добавить dependency-free Python policy scanner для tracked-файлов. Он проверяет
опасные имена и расширения, ограничение размера и небольшой набор
высокодостоверных сигнатур секретов. Значения секретов никогда не выводятся.

Дополнить release-controller Gateway проверкой равенства текущей Alembic
revision БД и head подготовленного релиза до атомарного переключения `current`.
Forward-активация fail-closed. Явный rollback пропускает равенство head, потому
что совместимые forward-миграции могут уже опережать старый код.

## Альтернативы

- Полагаться на памятку с командами: отклонено, потому что пропуск не является
  машинно обнаруживаемой ошибкой.
- Добавить GitHub Actions: отклонено из-за ненужной внешней зависимости и
  границы приватного домашнего контура.
- Автоматически запускать миграции внутри `deploy`: отклонено, потому что
  изменение БД должно оставаться отдельным явным действием и иметь понятную
  точку невозврата.
- Проверять только наличие новых migration-файлов локально: отклонено, потому
  что локальный репозиторий не знает фактическую revision production-БД.
- Запрещать rollback при несовпадении code head: отклонено, потому что это может
  лишить оператора безопасного отката к обратно совместимому коду.

## Последствия

Положительные:

- релиз имеет одну воспроизводимую локальную точку допуска;
- Gateway нельзя активировать поверх неподготовленной схемы;
- случайные секреты и тяжёлые артефакты блокируются до commit/deploy;
- внешний CI и новые runtime-зависимости не появляются;
- длительность каждой проверки сохраняется для будущей оптимизации.

Отрицательные:

- полный gate занимает больше времени, чем отдельный unit-test;
- для визуальной проверки нужен локальный Edge или Chrome;
- новый migration-релиз требует три явные команды вместо короткого `deploy`;
- policy scanner намеренно не является универсальным entropy-анализатором и не
  гарантирует обнаружение любого возможного секрета.
