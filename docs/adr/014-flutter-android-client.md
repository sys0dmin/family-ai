# Flutter-клиент для Android

## Статус

Принято

## Контекст

Детскому интерфейсу требуется Android-приложение с визуальной навигацией,
микрофоном и воспроизведением голоса. Серверные агенты, история, безопасность и
provider abstractions уже принадлежат Gateway. Основная среда разработки на
Windows — VS Code, без обязательного использования Android Studio.

Адрес Gateway зависит от домашней сети и не должен быть встроен в приложение.
Текущее LAN-развёртывание использует HTTP.

## Решение

Создать независимый Flutter-клиент в `mobile/`. Он обращается только к стабильным
REST API Gateway и не дублирует серверную бизнес-логику. Flutter выбран как
кроссплатформенный UI toolkit с официальной поддержкой VS Code и прямым доступом
к Android audio APIs через заменяемые плагины.

Родитель вручную вводит адрес Gateway. Клиент нормализует `http`/`https` URL,
запрещает credentials, query, fragment и произвольный path, проверяет `/healthz`
и сохраняет адрес через `shared_preferences`. Адрес не считается секретом.

Android-клиент временно разрешает cleartext HTTP для домашней сети. Секреты и
токены через такой канал передаваться не должны. Для внешнего доступа потребуется
HTTPS и пересмотр network security policy.

Запись и воспроизведение голоса скрыты за клиентским интерфейсом `VoiceSession`.
Реализация записывает временный WAV 16 кГц/моно, удаляет его после отправки и
проигрывает бинарный TTS-ответ Gateway. Экран диалога не зависит от конкретных
Flutter audio plugins. Серверная история остаётся источником распознанного
текста и ответа; исходное аудио не сохраняется.

Ответы агента кешируются локально через отдельный интерфейс `VoiceReplyCache`.
Ключ кеша состоит из идентификаторов разговора и сообщения. При промахе клиент
повторно синтезирует сохранённый текст через Gateway, не дублируя TTS-логику.
Кеш ограничен 10 днями и 100 МБ и удаляется вместе с очищаемым разговором.
Исходные записи ребёнка намеренно не кешируются.

Gateway финализирует размеры контейнера потоковых WAV-ответов провайдера.
Android-клиент повторяет эту нормализацию перед кешированием как защиту от
старой версии Gateway или другого совместимого TTS-провайдера.

## Альтернативы

- Capacitor/WebView: отклонён как основной фундамент из-за дополнительной
  сложности разрешений микрофона, воспроизведения аудио и поведения WebView.
- Нативный Kotlin/Jetpack Compose: технически подходит, но увеличивает стоимость
  разработки и не даёт преимуществ для текущего кроссплатформенного UI.
- PWA: подходит для быстрого ярлыка, но хуже контролирует voice-first UX и
  разрешения устройства.
- Захардкоженный IP Gateway: отклонён, потому что связывает сборку приложения с
  конкретной домашней адресацией.

## Последствия

Положительные: серверные сервисы остаются независимо заменяемыми; адрес можно
изменить без пересборки; VS Code достаточен; будущая iOS-версия сможет повторно
использовать клиентский код.

Отрицательные: UI браузера и Flutter развиваются как два клиента; требуется
Android toolchain; LAN HTTP осознанно ограничивает безопасную область применения
домашней сетью.
