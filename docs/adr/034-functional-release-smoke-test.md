# Сквозной функциональный smoke-test Gateway-релиза

## Статус

Принято

## Контекст

Проверка systemd и `/healthz` подтверждает только запуск процессов. Она не
обнаруживает несовместимость Admin UI, недоступность PostgreSQL и ошибки
настроенных LLM, STT, TTS или Vision-провайдеров. Поэтому релиз мог считаться
успешным, хотя основной пользовательский сценарий уже не работал.

Обычные детские API нельзя использовать для автоматической проверки: они
создают историю диалога и могут повлиять на долгосрочную память и статистику.

## Решение

Gateway release-controller после liveness health-check запускает отдельный
HTTP smoke-runner из точного активируемого Git release. Runner проверяет Admin
UI, Gateway с PostgreSQL и AI-провайдеры по стабильным production-контрактам.

Для LLM используется существующая защищённая stateless тест-студия. Её контракт
расширяется stateless-операциями STT и Vision. TTS генерирует короткую
синтетическую фразу, полученный буфер сразу используется как вход STT. Vision
получает детерминированное изображение, сгенерированное в памяти стандартной
библиотекой. Ни один этап не создаёт conversation, message, media, memory или
activity session.

Первый сбой останавливает проверку и возвращает стабильное имя этапа без тела
ответа и секретов. Не прошедший smoke-test Gateway-релиз не записывается как
успешный и откатывается на предыдущий код. Vision считается опционально
пропущенным только тогда, когда он явно отключён конфигурацией.

Исторический rollback не требует функционального runner в старом артефакте:
после возврата выполняется liveness health-check. Полный smoke-test можно
повторить отдельной операторской командой с Gateway-хоста.

## Альтернативы

### Расширить `/healthz` внешними вызовами

Отклонено: liveness endpoint должен быть быстрым, безопасным и не зависеть от
платных или медленных AI-провайдеров.

### Проверять обычный голосовой или мультимодальный API

Отклонено: это загрязняет детскую историю, статистику и потенциально память.

### Запускать проверки только вручную из Admin UI

Отклонено: оператор может забыть проверку, а release-controller уже успеет
зафиксировать неисправную версию как успешную.

### Развернуть отдельный сервис синтетического мониторинга

Отклонено для домашнего контура: новая постоянно работающая служба не нужна для
редкой post-deploy проверки.

## Последствия

Положительные:

- успешный Gateway-релиз подтверждает основной функциональный контур;
- ошибка локализуется по стабильному имени этапа;
- тестовые данные синтетические, краткоживущие и не попадают в БД;
- отдельные сервисы и provider-интерфейсы остаются заменяемыми.

Отрицательные:

- Gateway deploy становится дольше и выполняет реальные provider-запросы;
- временная внешняя ошибка провайдера может вызвать откат исправного кода;
- после отдельного Speech deploy оператору нужно повторить smoke-команду с
  Gateway-хоста, чтобы проверить полный контур.
