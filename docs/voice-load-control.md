# Управление перегрузкой Voice

## Зачем это нужно

Speech Service работает на Intel J3710. Production-замер этапа 19 показал:

| Одновременных клиентов | Total p95 | Максимальная очередь Speech |
| ---: | ---: | ---: |
| 1 | 14,5 с | 0 |
| 2 | 25,0 с | 1 |
| 4 | 49,0 с | 3 |

При четырёх клиентах CPU Speech достиг p95 `94,4%`. Поэтому Gateway по
умолчанию принимает не более двух полных voice-turn одновременно: один может
выполняться в Speech, второй — кратко ждать. Третий не ставится в бесконечную
очередь и получает быстрый ответ `429`.

Ограничение общее для:

- обычного и потокового `/v1/voice/.../turn`;
- обычного и потокового `/v1/multimodal/.../turn`;
- повторного озвучивания сохранённого ответа.

## Жизненный цикл запроса

Android создаёт случайный `X-Request-ID`. Gateway занимает слот до полного
завершения ответа. Для streaming слот освобождается также при ошибке, разрыве
соединения или выходе из voice screen. Android отменяет локальную подписку и
отправляет best-effort `DELETE /v1/voice/streams/{turn_id}` для уже созданного
TTS-потока.

Повторная отправка того же ID во время обработки и пять минут после неё
отклоняется до обращения к провайдерам. В памяти остаются только UUID и время;
аудио, фото, транскрипция и ответ не сохраняются ограничителем.

## Временные бюджеты

| Этап | Значение по умолчанию | Допустимый диапазон |
| --- | ---: | ---: |
| STT | 60 с | 5–120 с |
| LLM | 20 с | 5–120 с |
| TTS | 30 с | 5–120 с |

Бюджет TTS потокового ответа охватывает весь синтез, а не только появление
первой части. При превышении бюджета обычный API возвращает `504`, streaming —
событие `voice_timeout`. Android показывает короткое понятное сообщение и не
предлагает ребёнку бесконечно ждать. Для STT timeout сообщение прямо просит
повторить короткую фразу и не создаёт впечатление, будто Алиса или другой агент
не смог придумать ответ.

## Ответы API

- `409 Conflict` — этот `X-Request-ID` уже обрабатывался;
- `429 Too Many Requests` — два voice-turn уже заняты; заголовок
  `Retry-After: 3` подсказывает минимальную паузу;
- `504 Gateway Timeout` — STT, LLM или TTS превысил свой бюджет.

Во всех случаях возвращается `X-Request-ID`, когда он известен. Внешняя ошибка
не раскрывает внутренний endpoint или исключение провайдера.

## Управление из Admin

Во вкладке «Настройки», в блоке Speech, доступны:

- число одновременных voice-turn;
- бюджеты STT, LLM и TTS.

Поля проходят тот же безопасный цикл preview → redacted diff → атомарная запись
→ restart Gateway → readiness → автоматический rollback. Значения становятся
активными только после перезапуска Gateway.

Во вкладке «Инфраструктура» строка Voice Pipeline показывает:

- `Voice slots` — активные слоты и общую ёмкость;
- `Отклонено` — сумму duplicate- и capacity-rejection текущего процесса;
- очередь Speech, ошибки и отмены рядом с уже существующими метриками.

Счётчики сбрасываются при перезапуске Gateway и служат оперативной диагностикой,
а не долговременной аналитикой.

## Эксплуатационная проверка

1. Убедиться, что `Voice slots` показывает `0 / 2` в покое.
2. Запустить два голосовых запроса почти одновременно — оба должны быть приняты.
3. Пока они выполняются, отправить третий — Android должен быстро сообщить, что
   голос занят, а `Отклонено` увеличится.
4. Повторить запрос с тем же `X-Request-ID` — получить `409`, не создавая новой
   работы STT/LLM/TTS.
5. Выйти с voice screen во время ответа — число активных слотов должно вернуться
   к нулю после отмены потока.
6. Для проверки timeout временно уменьшать бюджет можно только через Admin с
   последующим возвратом прежней ревизии. Не использовать production-аудио
   ребёнка как тестовый материал.

Технические события конкретной ошибки доступны в диагностической временной
шкале по `request_id`; правила приватности описаны в
[`request-tracing.md`](request-tracing.md). Архитектурное решение — в
[`ADR 041`](adr/041-bounded-voice-execution.md).
