# Участие в разработке Family AI Mentor

Спасибо за интерес к проекту. Family AI Mentor работает с детским контекстом,
поэтому корректность, приватность и понятность изменений важнее скорости.

## Перед началом

1. Создайте issue с кратким описанием проблемы или предложения.
2. Для архитектурного изменения опишите границы сервисов и совместимость API.
3. Не добавляйте новую зависимость без объяснения необходимости и альтернатив.
4. Значимые технические решения оформляйте ADR в `docs/adr/`.

## Локальная разработка

```bash
docker compose up -d postgres
cp .env.example .env
uv sync --all-groups
uv run alembic upgrade head
uv run uvicorn gateway.app.main:app --reload --port 8000
```

Настройте собственные provider credentials только в `.env`. Этот файл исключён
из Git и не должен попадать в issue, pull request, логи или скриншоты.

## Проверки перед pull request

Минимальный набор:

```bash
uv run ruff check .
uv run pytest
```

На Windows полный release gate запускается так:

```powershell
.\scripts\release\Invoke-LocalReleaseGate.ps1
```

Если изменение затрагивает Flutter, Admin UI, миграции или развёртывание,
выполните соответствующие проверки из `docs/release-gate.md`.

## Требования к изменениям

- сохраняйте обратную совместимость API, если её нарушение не согласовано;
- бизнес-логика принадлежит Gateway, а поведение персонажей — конфигурации;
- провайдеры LLM, Vision, STT и TTS подключаются через стабильные интерфейсы;
- изменения схемы PostgreSQL выполняются только миграциями Alembic;
- новые настройки документируются и получают безопасные значения по умолчанию;
- исправление критического поведения сопровождается regression test;
- документация обновляется в том же pull request.

## Детские данные и приватность

Никогда не добавляйте в Git:

- записи голоса, фотографии или полные сообщения ребёнка;
- реальные имена, адреса, расписания и другие идентифицирующие сведения;
- домашние IP-адреса, доменные имена и дампы production-конфигурации;
- API-ключи, пароли, токены, приватные ключи и диагностические пакеты.

Для тестов используйте вымышленные обезличенные данные. Если ошибка
воспроизводится только на реальном материале, опишите технические признаки без
публикации исходного содержимого.

## Pull request

В описании укажите:

- что изменено и зачем;
- какие риски и альтернативы рассмотрены;
- как проверялось изменение;
- затронуты ли privacy, safety, API, БД или эксплуатация;
- требуется ли миграция или новая переменная окружения.

Небольшие, цельные изменения проверять и сопровождать проще, чем большие
переписывания нескольких независимых компонентов.

## Лицензирование вклада

Отправляя вклад в репозиторий, вы соглашаетесь распространять его на условиях
лицензии MIT проекта. Не добавляйте материалы, на публикацию которых у вас нет
прав, и указывайте происхождение и лицензию допустимых сторонних материалов.
